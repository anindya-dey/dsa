A file on your laptop is a name, some bytes, and a folder. At industrial
scale that design collapses: folders are a hierarchy someone must
maintain, a file can be modified mid-read, and one machine's disk is
both a capacity limit and a failure domain. **Object storage** is the
answer the industry converged on, and the design is defined by what it
gave up: no folders, no partial updates, no locking. What remains is
almost embarrassingly simple and almost limitlessly scalable: **store
an immutable blob of bytes under a flat key; retrieve it by that key;
that is the entire interface.**

S3, GCS, Azure Blob are this design, and their numbers are the reason
it won: effectively unlimited capacity, 11 nines of durability (by
replication and [erasure coding](https://en.wikipedia.org/wiki/Erasure_code)
across facilities, not by being careful), key-addressed reads in tens of
milliseconds, and per-gigabyte costs that make deleting data a
*decision* rather than an assumption.

## The design, from the constraint up

The interface is deliberately smaller than a file system's, and every
removed feature is a scalability decision:

- **Flat namespace, not hierarchy.** Objects are addressed
  `bucket/key`, where the key is an arbitrary string. The "folder" you
  see in a browser is a naming convention (`photos/2024/pic.jpg`), and
  the store does not know or care: no directory metadata to maintain,
  no renames, no moves, no tree rebalancing. The *appearance* of
  structure lives entirely in the key names, which is why key *design*
  (unique, sortable, queryable-by-prefix) is the actual modeling
  decision, and prefix-listing is how "folders" become real.
- **Immutable objects.** You write an object whole, and you replace it
  whole (a new object under the same key, replacing atomically); there
  is no partial write, no append-with-offset, no in-place edit.
  Immutability is what makes replication trivial (a copy of an
  immutable object cannot diverge), what makes
  [caching](/system-design/fundamentals/cdn) trivial (an immutable object
  can be cached forever), and what makes versioning possible (keep the
  old bytes, they never change).
- **Eventual consistency for listing.** A just-written object is
  readable by key essentially immediately in modern systems, but the
  *listing* of a prefix may lag: the store's index eventually catches
  up. The failure mode to know: code that writes then immediately lists
  to "check" its own write.
- **Metadata, not structure.** An object carries a small map
  (content-type, custom headers, size, timestamps), set at write time,
  readable on read: enough to serve a web page (content-type), enforce
  access (signed
  [URLs](/system-design/fundamentals/auth-basics)), and drive
  [lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lifecycle-mgmt.html)
  rules (expire, archive, delete by prefix and age). No schema, no
  query: if you need "objects where color=red", the answer is either
  key design or an index elsewhere.

## The access model

Access is the part that surprises people coming from files: objects
are private by default, and access is *delegation*, not
permissions-lists-on-folders. The patterns worth knowing:

- **Pre-signed URLs**: a URL that grants time-limited access to one
  object, generated by a service that authenticated the user. The
  standard upload/download pattern for user content: your app signs a
  URL for "user 42 may write to uploads/42/x.jpg for 15 minutes", and
  the bytes go browser-to-storage without transiting your servers,
  which is why an S3-backed upload feature costs your API almost
  nothing.
- **CDN in front**: since objects are immutable, they are the perfect
  [edge](/system-design/fundamentals/cdn) content, and most object
  traffic in a consumer product is served this way (the origin sees
  first requests only).
- **Serving through compute or direct**: either an app server streams
  the bytes (simple, expensive: your bandwidth, your latency) or the
  client gets a signed URL (cheap, and the storage's bandwidth is
  the point of it).

## What it is for, and the honest limits

The canonical payloads: user content (photos, video, documents) at any
scale; the
[data lake](/system-design/fundamentals/olap-vs-oltp) substrate
(parquet files, raw event archives, re-derivable truth);
[static assets](/system-design/fundamentals/cdn) and backups
(snapshot, replicate, done); and any large binary that a database
should not hold in a row.

The limits are the flip side of the design, and each one has a
standard "so use the right tool":

- **No queries.** Key-addressed only, so "find objects by content" is
  a no, and search needs an
  [inverted index](/system-design/fundamentals/search-and-inverted-index)
  elsewhere with the object store behind it.
- **No transactions.** Two objects are written by two calls, and
  "these must both succeed" is your problem: usually solved by making
  one object the truth and the rest derived, or by an
  [outbox](/system-design/fundamentals/distributed-transactions).
- **No updates.** Rewriting a 5 GB object to change one byte is the
  design's price, and the workarounds (chunking, compaction, the
  [LSM-tree](https://en.wikipedia.org/wiki/Log-structured_merge-tree)
  lineage that databases built on top) are how "mutable store" gets
  built *out of* immutable objects, which is the deepest lesson in this
  design: immutability plus compaction is a general-purpose recipe, and
  it is also exactly how
  [event stores](/system-design/fundamentals/event-sourcing-and-cqrs)
  and log systems work.
- **Latency floor.** Tens of milliseconds per read: fine for
  big objects and cold data, wrong for the
  [hot key](/system-design/hld/distributed-cache), which is
  what the memory tiers are for.
