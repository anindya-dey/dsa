title: "Feature/Model Backfills & Migrations"
summary: "Recomputing history and migrating models without breaking production."
---

Two related operations, both *unavoidable* in a maturing ML system,
and both *migrations* in the [strangler](/system-design/hld/large-scale-migration)
sense: a **backfill** recomputes a feature (or a model's outputs)
*over historical data* (a new feature needs its history; a bug fix
changes every value), and a **model migration** replaces a model
(or its base, or its features) across production. Both are
"change a thing that has years of derived state depending on it,"
which is the hardest kind of change, and the discipline is the same
one the [large-scale-migration](/system-design/hld/large-scale-migration)
page teaches: *incremental, dual-run, reconciled*.

## Backfills: recomputing history

The problem: a feature is defined by a computation
([the feature-engineering page](/system-design/ai-ml/feature-engineering-basics)),
and the *history* of that feature is whatever the old computation
produced — so when the computation *changes* (a bug fixed, a window
resized, a new [embedding model](/system-design/ai-ml/embeddings-vector-representations)),
the historical values are *wrong*, and the training set built on
them is wrong. A **backfill** recomputes the feature over the past.

The design, and its hazards:

- **Replay the source** (the backfill is a [batch
  job](/system-design/fundamentals/stream-vs-batch-processing) over
  the [event log](/system-design/fundamentals/event-sourcing-and-cqrs)
  (the raw events are immutable, so the history is *recomputable*:
  the payoff of event sourcing) — the same [training-data
  pipeline](/system-design/ai-ml/training-data-pipelines), run with
  a historical *as-of* window per timestamp (the
  [point-in-time](/system-design/ai-ml/training-data-pipelines)
  discipline: the backfill must produce the values *as they would
  have been*, not "as of now").
- **The consistency hazard** (the *offline* store is backfilled, but
  the *online* store now has the *new* computation's values: a
  training set from the backfilled history must match what serving
  produces — the [training/serving
  skew](/system-design/ai-ml/feature-engineering-basics), *created
  by the backfill* if the two computations differ: the backfill and
  the new serving computation must be *the same code* — the
  [one-definition](/system-design/ai-ml/feature-stores) rule, and
  the reason a backfill is a *code deployment* as much as a data
  job).
- **Cost and time** (recomputing years of features is a
  [warehouse-scale](/system-design/fundamentals/olap-vs-oltp) job
  (hours to days): the backfill runs *alongside* production
  (the [dual-run](/system-design/hld/large-scale-migration)
  discipline), not instead of it).
- **The version boundary** (the historical values have a *version*
  (which computation produced them), and mixing versions in one
  training set is a [silent bug](/system-design/ai-ml/data-versioning-lineage):
  the backfill *creates a new data era*, and the [lineage](/system-design/ai-ml/data-versioning-lineage)
  records the boundary — "before the backfill" and "after" are
  *different datasets*).

## Model migrations: replacing a model in production

The problem: a model is *embedded* in a system (the
[features](/system-design/ai-ml/feature-stores) it consumes, the
[pipeline](/system-design/ai-ml/mlops-cicd) that serves it, the
[downstream](/system-design/hld/fraud-detection) that consumes its
outputs), so replacing it is a *migration*, not a swap. The common
cases: a **base-model upgrade** (a new [LLM](/system-design/ai-ml/llm-serving)
version, a new [embedding model](/system-design/ai-ml/embeddings-vector-representations):
*re-embed everything*, the [vector-database era
migration](/system-design/ai-ml/vector-databases)), a **feature
change** (the model now consumes a new feature: the
[serving tier](/system-design/ai-ml/model-serving-architectures)
and the training set must both change), and a **framework change**
(a new [runtime](/system-design/ai-ml/model-runtimes-compilation):
the compiled artifact changes).

The design, and the [strangler](/system-design/hld/large-scale-migration)
applied:

- **Dual-run** (the old and new models *both* serve (shadow or
  canary): the [shadow deployment](/system-design/ai-ml/offline-vs-online-evaluation),
  comparing outputs and metrics — the migration *validates* before
  it cuts over).
- **Dual-write the derived state** (the new embedding is computed
  *alongside* the old, the new feature *alongside* the old: both
  stored, both versioned, so the rollback is a *pointer*, not a
  rebuild — the [version-matrix](/system-design/ai-ml/multi-model-serving-routing)
  during the transition).
- **Cut over incrementally** (route a percentage to the new model,
  watch the guardrails, promote: the [canary](/system-design/fundamentals/reliability-engineering)
  discipline, and the [A/B](/system-design/ai-ml/ab-testing-experimentation)
  platform, doing the migration's validation).
- **Retire the old** (the [strangler's ending](/system-design/hld/large-scale-migration):
  the old model, its embeddings, its features are *deleted* —
  or the migration never finishes and the version matrix grows
  forever: the "last 10%" trap, with a decommission budget).

## Why these are the hard cases

Both backfills and migrations are hard for the same reason: **they
change a *shared* derived artifact with *years* of dependents.** The
[lineage](/system-design/ai-ml/data-versioning-lineage) is what makes
them *tractable* (you can *see* the dependents: "which models use
this feature" is a query), the [dual-run](/system-design/hld/large-scale-migration)
is what makes them *safe* (validate before cutting over), and the
[versioned artifacts](/system-design/ai-ml/model-registry) are what
make them *reversible*. Without those, a backfill is a leap of
faith and a model migration is a rewrite — which is the whole
argument for building the lineage and registry machinery *before*
you need it, because the migration is when you need it most.
