---
title: "Serverless Inference & Cold Starts"
summary: "Scale-to-zero for models, and the multi-gigabyte cold start that fights it."
---

Serverless inference ("scale to zero, pay per request") is the
dream for the *long tail* of models — the hundreds that get a
handful of calls an hour, where a [dedicated
fleet](/system-design/ai-ml/gpu-accelerator-management) is 99% idle
and therefore 99% wasted money. The mechanism (a request arrives →
the platform starts a container with the model → it answers →
the container scales down after idle) is the standard serverless
pattern, and it collides with the ML-specific reality head-on: **a
model is a multi-gigabyte artifact whose load takes seconds to
minutes**, so the *cold start* is not milliseconds (the web-
function case) but *seconds* — the user waits, the request times
out, or the platform keeps a warm pool (which is no longer
scale-to-zero). The whole design is the negotiation between
scale-to-zero and the cold start.

## The cold start, decomposed

The latency of a cold inference, in its stages — because the
optimization targets *each*:

```mermaid
graph LR
    R[Request arrives] --> S[Schedule: find a node]
    S --> P[Provision: start the container/VM]
    P --> D[Download: fetch the model artifact]
    D --> L[Load: into RAM/VRAM, init runtime]
    L --> W[Warm-up: first inference, GPU init]
    W --> A[Answer]
```

- **Scheduling/provisioning** (seconds: the orchestrator finds
  capacity and starts the sandbox — the generic serverless cost).
- **Download** (the *ML-specific* cost: a 5 GB model from
  [object storage](/system-design/fundamentals/object-storage) is
  seconds-to-minutes, and it dwarfs the generic cold start — the
  fix is the [warm pool](/system-design/ai-ml/model-caching-warm-pools)
  or the model cached *on the node*).
- **Load + warm-up** (the model into VRAM, the runtime's init, the
  [compiled engine's](/system-design/ai-ml/model-runtimes-compilation)
  first pass: more seconds, and the GPU init is the sticky part).

The honest total: a naive serverless GPU cold start is *30 seconds
to minutes*, which no interactive request tolerates, which is why
naive serverless inference works only for *tolerant* workloads
(batch-ish, async, or internal).

## The mitigations, priced

The design's real content, in the order to apply them:

- **Keep a warm floor** (the platform holds N warm instances: the
  "serverless" that is not: the honest answer for *interactive*
  models, and it is a [capacity-planning](/system-design/fundamentals/capacity-planning-and-estimation)
  decision — how many warm, at what cost, to cover the traffic
  floor).
- **Snapshot/restore** (checkpoint the *loaded* state — the model in
  VRAM, the runtime initialized — and restore it on cold start:
  the modern technique (AWS's model-snapshot, the "restore the
  process" idea) that cuts the load+warmup to *sub-second*, turning
  serverless into a real option for interactive models — the
  [caching](/system-design/fundamentals/caching) idea, at process
  scale).
- **Smaller models on the edge of serverless** (the
  [quantized](/system-design/ai-ml/inference-optimization) model
  loads in a fraction of the time: a 500 MB int8 model has a much
  friendlier cold start than a 10 GB fp16 one — the
  [optimization](/system-design/ai-ml/inference-optimization) page,
  again, paying off in a new dimension).
- **Node-local model cache** (the model already *on the node* (from
  a previous instance, from a node-init pull): the
  [warm-pool](/system-design/ai-ml/model-caching-warm-pools)
  primitive, and the reason a serverless ML platform is really a
  [cache](/system-design/fundamentals/caching) with a scheduler).
- **Request coalescing / queueing** (a cold-starting instance
  *queues* the arriving requests (the [chat
  design's](/system-design/hld/chat-application) long-poll: the
  first request triggers the start, later ones join it) — the
  request that pays the cold start is the *one*, not *all* of them,
  which is the same single-flight discipline as the
  [cache-stampede](/system-design/fundamentals/caching) fix).

## The fit: where serverless actually wins

The honest product positioning:

- **The long tail of low-traffic models** (the per-tenant fine-tune
  called 10 times an hour: dedicated is wasteful, warm-forever is
  wasteful, serverless is *right* — the [multi-model
  routing's](/system-design/ai-ml/multi-model-serving-routing)
  cold tier).
- **Bursty/experimental** (an internal model, a prototype, a
  rarely-used admin tool: no traffic floor to cover).
- **Async/batch-tolerant** (a request that can wait seconds:
  the [batch-vs-realtime](/system-design/ai-ml/batch-vs-real-time-prediction)
  axis, the models where the cold start is *invisible*).
- **Not** the interactive high-traffic models (the warm floor is
  the answer, and that is not scale-to-zero: the honest admission
  that "serverless inference" and "interactive LLM" are in tension,
  which the snapshot technique is narrowing).
