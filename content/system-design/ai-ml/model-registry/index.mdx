title: "Model Registry & Versioning"

A model registry is the **system of record for models** — the
[artifact store](/system-design/fundamentals/object-storage) plus
the metadata that makes the artifacts *usable*: which version is
which, where it is in its [lifecycle](#stages), what data and code
produced it ([lineage](/system-design/ai-ml/data-versioning-lineage)),
and how it performed ([evaluation](/system-design/ai-ml/evaluating-llm-systems)).
Without one, "which model is in production, and can we rebuild it"
is a Slack archaeology problem; with one, it is a query. The design
is the [metadata-plane](/system-design/hld/object-storage-system)
pattern (small, strongly-consistent metadata; large, immutable
artifacts), model-shaped.

## What a registry holds

- **The artifact** (the weights file: hundreds of MB to GB, in
  [object storage](/system-design/fundamentals/object-storage), the
  registry storing the *reference*, not the bytes — the
  [content-addressed](/system-design/hld/distributed-file-storage)
  discipline, so the artifact's hash is its identity).
- **The metadata** (the *rows*: model name, version, stage,
  creation time, owner, the [lineage](/system-design/ai-ml/data-versioning-lineage)
  (dataset hash, code sha, hyperparameters), the eval results, the
  framework and format, the size: the queryable facts).
- **The stage** (the lifecycle label: `staging` / `production` /
  `archived` (or `candidate` / `shadow` / `production` / `retired`):
  the registry's answer to "what is deployed" — a *pointer* that
  the [serving tier](/system-design/ai-ml/model-serving-architectures)
  resolves, so "deploy v8" is a *stage transition*, not a redeploy).

## Versioning: the discipline

- **Immutable versions** (a registered version never changes: a fix
  is a *new* version, the
  [append-only](/system-design/fundamentals/event-sourcing-and-cqrs)
  discipline — so "model v7" means the same thing forever, and a
  rollback is a pointer move, not a rebuild).
- **Semantic-ish versioning** (versions carry *meaning*:
  a patch (retrained on fresh data), a minor (new features), a
  major (new architecture): the [release
  conventions](/system-design/fundamentals/reliability-engineering)
  applied to models, so "we shipped a major" flags a bigger change
  than "we retrained").
- **The stage as a pointer** (production points at *one* version
  (or a set, during a [canary](/system-design/fundamentals/reliability-engineering));
  promotion is `v8 → production`, and the *previous* production
  version is retained for rollback — the
  [blue-green](/system-design/fundamentals/reliability-engineering)
  idea, as a registry operation).

## Why it matters (the queries it answers)

The registry's value is the *questions* it makes cheap, each a
production necessity:

- **"What is in production right now?"** (the stage pointer: the
  [observability](/system-design/fundamentals/observability)
  question, answerable in one lookup — and the
  [decision log](/system-design/hld/fraud-detection)'s "which model
  scored this" resolves against it).
- **"Can we rebuild production?"** (the lineage: the dataset hash +
  code sha + hyperparameters → a rerun: the
  [reproducibility](/system-design/ai-ml/reproducibility-metadata)
  promise, *delivered* by the registry).
- **"What changed between v7 and v8, and did it help?"** (the eval
  results and lineage diff: the model-comparison query, and the
  [A/B](/system-design/ai-ml/ab-testing-experimentation) evidence).
- **"Which models depend on this dataset / this feature / this base
  model?"** (the *reverse* lineage: the blast radius of a data fix
  or a base-model deprecation — the
  [migration](/system-design/ai-ml/feature-model-backfills)
  planning query, and a real one when a base LLM is retired).

## The systems shape

The registry is a **metadata service** (a small, transactional
database: the versions, stages, lineage edges — the *strong* plane)
in front of an **artifact store** (the [object
storage](/system-design/fundamentals/object-storage): the immutable
blobs — the *dumb* plane), with the [serving
tier](/system-design/ai-ml/model-serving-architectures) and the
[pipeline](/system-design/ai-ml/mlops-cicd) as its clients. The
[multi-model routing](/system-design/ai-ml/multi-model-serving-routing)
resolves *which artifact* to load *through* the registry's stage
pointer; the [warm pool](/system-design/ai-ml/model-caching-warm-pools)
caches the *loaded* artifacts; and the registry is the
*authoritative* answer to "what should be loaded." The separation
(the registry knows *what*; the serving tier knows *where it is
loaded*) is the same
[metadata/data-plane split](/system-design/hld/object-storage-system)
as every artifact system on this site.
