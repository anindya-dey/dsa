title: "Linear Structures"
summary: "Arrays, linked lists, and deques: choose sequence storage by the operations you need."

A **linear structure** stores elements in a sequence: one after another.
The important choice is how that sequence is stored. The same values
can be easy to index in an array or easy to rearrange in a linked list.
Neither choice makes every operation cheap.

Consider `[10, 20, 30]`. You want the value at index 2, then you want to
insert 15 between 10 and 20. An array makes the first task direct. A
linked list can make the second task cheap, provided you already know
where to insert. Index 2 is the third element because indices start at 0.

## Arrays: quick access by position

A dynamic array, such as `std::vector<int>`, stores elements next to each
other in **contiguous memory**. You can calculate where an index belongs
without walking through earlier elements, so indexed access is O(1).
A processor's **cache** is small, fast memory. Nearby array elements often
share cached data, making scans efficient. Actual speed depends on the
machine and workload.

To insert 15 into `[10, 20, 30]`, you shift 20 and 30 one position to the
right, then write 15 into the gap. Inserting or erasing near the front
can move almost every element, so the worst-case cost is O(n).

Appending usually needs just one write. When capacity runs out, the
vector gets a larger buffer and relocates its elements. One append can
therefore cost O(n), while ordinary appends are
[O(1) amortized](/dsa/patterns/asymptotic-analysis#amortized-paying-for-the-expensive-rare-case).
The capacity does not have to double. `reserve()` can prevent
reallocation until the reserved capacity is exceeded, but it does not
remove the shifts needed for middle insertions.

## Linked lists: quick edits at known positions

A linked list stores **nodes**. Each node holds a value and a link to the
next node. A doubly linked list also keeps a link to the previous node.
The nodes do not have to sit next to one another in memory.

To insert 15 after the node holding 10, point the new node at 20, then
point 10 at the new node. You change two links rather than shift 20 and
30. Linking or unlinking one node is O(1) once you have the necessary
position information. A singly linked deletion may also need the
previous node, so finding that node can add a walk.

Finding index 2 means following links from the head. Finding an
arbitrary index or value takes O(n) in the worst case. Lists also need
memory for links, and following nodes often makes less use of the cache
than scanning an array. Those are trade-offs, not guarantees about
every implementation.

## Deques, stacks, and queues

An array and a linked list are not the only layouts. A `std::deque`
typically stores elements in separate blocks. It provides O(1) indexed
access and insertion/removal at either end, but its elements are not
one contiguous array. Middle edits still take O(n) in the worst case.

A **stack** and a **queue** describe access rules rather than memory
layouts. A stack removes the most recently added item first. A queue
removes the oldest item first. You can implement these rules with
different storage: a vector works well for a stack; a deque, linked
list with a tail pointer, or circular buffer can support queue operations.
Simply erasing the front of a vector costs O(n).

## How to spot it

Use this topic when you need to build or change a sequence. Ask which
operations the problem repeats: indexed lookup, appending, removing
from the front, or editing a known position. This is the same storage
question listed in the [cheat sheet](/dsa/cheat-sheet).

| Storage | Indexed access | Add/remove at an end | Insert/erase in the middle |
| --- | --- | --- | --- |
| Dynamic array | O(1) | Back: append O(1) amortized, remove O(1); front: O(n) | O(n) worst case |
| Linked list | O(n) | O(1) with the required head/tail links | O(1) at a known position with the required links; O(n) to find it |
| Deque | O(1) | O(1) at either end | O(n) worst case |

Here `n` is the number of elements, and moving or destroying one element
is assumed to cost O(1). For a singly linked list, removing the tail
still needs its predecessor. Knowing the tail alone does not make that
operation O(1).

## Worked example: compact a sorted array

Suppose `nums = [1, 1, 2, 2, 3]`. You want each distinct value once at
the beginning, without creating another array. Keep two positions:
`read` examines the input, and `write` marks the next free output slot.
Sorted input matters: equal values are neighbors.
`std::size_t` is the C++ type used for container sizes and indices.

```cpp
#include <cstddef>
#include <vector>

std::size_t removeDuplicates(std::vector<int>& nums) {
    std::size_t write = 0;
    for (std::size_t read = 0; read < nums.size(); ++read) {
        if (write == 0 || nums[read] != nums[write - 1]) {
            nums[write] = nums[read];
            ++write;
        }
    }
    return write;
}
```

You keep the first 1, skip the second, keep 2, skip the next 2, then keep
3. The function returns 3, and the first three positions contain
`[1, 2, 3]`. It does **not** resize the vector; ignore the remaining
positions or resize it to the returned length.

The `write == 0` check handles the first value without accessing
`nums[write - 1]`. After that, compare with the last value you kept.

The output never overtakes the unread input, so writing a kept value
cannot destroy a value you still need. The scan takes O(n) time and
O(1) extra space. This read/write technique fits compaction; rotation
and backward merging use different pointer movements.

## Choose by the work you need

Use a vector when indexed access and sequential scans dominate. Consider
a linked list when edits at already-known nodes dominate. Use a deque
when you need both ends and indexing.

Linked lists can be sorted: `std::list::sort` is one example.
`std::sort` specifically needs random-access iterators: positions that can
jump directly by an offset. It works on vectors and deques, not linked
lists. Also remember that changing a container can invalidate saved
positions; reallocation and shifts are
different ways this can happen.
