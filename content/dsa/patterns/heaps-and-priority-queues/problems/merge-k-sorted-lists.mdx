## Problem

Given an array of `k` linked lists, each sorted in ascending order, merge
them into one sorted linked list and return its head.

**Constraints**

- `0 <= k <= 10^4`
- The total number of nodes is at most 10^4.
- `-10^4 <= Node.val <= 10^4`.

**Example**

```text
Input:  [1->4->5, 1->3->4, 2->6]
Output: 1->1->2->3->4->4->5->6
```

## Brute force

Collect every value into one array, sort it, and build a fresh list.

```cpp
ListNode* mergeKBrute(std::vector<ListNode*> lists) {
    std::vector<int> values;
    for (ListNode* head : lists) {
        for (ListNode* node = head; node != nullptr; node = node->next) {
            values.push_back(node->val);
        }
    }
    std::sort(values.begin(), values.end());

    ListNode dummy(0);
    ListNode* tail = &dummy;
    for (int value : values) {
        tail->next = new ListNode(value);
        tail = tail->next;
    }
    return dummy.next;
}
```

O(n log n) where n is the total node count, plus O(n) extra memory and a
full set of newly allocated nodes. It throws away the fact that the inputs
are already sorted, which is the entire structure the problem hands you.

A second brute force, merging the lists two at a time in sequence, is O(k·n)
in the worst case: each merge re-walks an ever-growing accumulator.

## Optimal: a heap of the current fronts

The k-way merge generalizes the two-list
[merge](/dsa/patterns/linked-list-manipulation/problems/merge-two-sorted-lists).
In the two-list version you compare the two heads and take the smaller.
With k lists, you compare k heads, and the heap is exactly the structure
that answers "which of these k is smallest" in O(log k) instead of O(k).

```cpp
ListNode* mergeKLists(std::vector<ListNode*>& lists) {
    auto cmp = [](ListNode* a, ListNode* b) {
        return a->val > b->val;            // min-heap by value
    };
    std::priority_queue<ListNode*, std::vector<ListNode*>, decltype(cmp)> heap(cmp);

    for (ListNode* head : lists) {
        if (head != nullptr) {
            heap.push(head);               // seed with each list's first node
        }
    }

    ListNode dummy(0);
    ListNode* tail = &dummy;

    while (!heap.empty()) {
        ListNode* smallest = heap.top();
        heap.pop();
        tail->next = smallest;             // splice the node itself
        tail = smallest;
        if (smallest->next != nullptr) {
            heap.push(smallest->next);     // advance that list
        }
    }
    return dummy.next;
}
```

Walk the logic: the heap holds the smallest not-yet-merged node from each
list. Popping the heap yields the globally smallest remaining node, which
is appended, and then that node's successor enters the heap as the list's
new front. Every node enters and leaves the heap once, so the total work
is O(n log k), and only O(k) extra memory holds the frontier. The dummy
head is the same
[list-splicing trick](/dsa/patterns/linked-list-manipulation) as the
two-list merge.

The `cmp` deserves a note: C++'s `priority_queue` is a max-heap by
default, so the comparator returns `a->val > b->val` to invert it into a
min-heap. Forgetting the inversion is the classic bug, and it silently
merges the lists in reverse.

## Complexity

| Approach | Time | Space |
| --- | --- | --- |
| Collect, sort, rebuild | O(n log n) | O(n) |
| Sequential two-list merges | O(k·n) worst | O(1) |
| Heap of fronts | O(n log k) | O(k) |

The heap wins when k is large and n is not much larger, and it is the
general template for merging any k sorted sources: sorted lists, log
streams, or [sorted files on disk](/system-design/hld/log-aggregation-system).
