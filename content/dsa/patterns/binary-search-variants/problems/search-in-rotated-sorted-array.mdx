## Problem

An array sorted in ascending order has been rotated between 1 and n times.
Given the rotated array `nums` and a `target`, return the index of `target`,
or -1 if it isn't present. The array contains no duplicates.

**Constraints**

- `1 <= n <= 5000`
- `-10^4 <= nums[i], target <= 10^4`
- All values are unique.

**Example**

```text
Input:  nums = [4,5,6,7,0,1,2], target = 0
Output: 4
```

## Brute force

Walk the array and return the index where the target appears.

```cpp
int searchBruteForce(const std::vector<int>& nums, int target) {
    for (int i = 0; i < static_cast<int>(nums.size()); ++i) {
        if (nums[i] == target) {
            return i;
        }
    }
    return -1;
}
```

Correct, but O(n), and it ignores the structure the problem handed you. The
whole point of the rotation setup is that the data is *almost* sorted, and
almost sorted still supports binary search.

## Optimal: modified binary search

The key observation: take any midpoint in a rotated sorted array. One of the
two halves is always perfectly sorted (the rotation break can only fall on
one side). Compare `nums[mid]` with `nums[lo]` to find out which half is
sorted, then check whether the target falls inside that sorted half's range.
One comparison narrows to a sorted half, the other to the messy half, but
either way you discard half the array and the halving continues.

```cpp
int search(const std::vector<int>& nums, int target) {
    int lo = 0;
    int hi = static_cast<int>(nums.size()) - 1;

    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;
        if (nums[mid] == target) {
            return mid;
        }

        if (nums[lo] <= nums[mid]) {                  // left half is sorted
            if (nums[lo] <= target && target < nums[mid]) {
                hi = mid - 1;                         // target inside left half
            } else {
                lo = mid + 1;
            }
        } else {                                      // right half is sorted
            if (nums[mid] < target && target <= nums[hi]) {
                lo = mid + 1;                         // target inside right half
            } else {
                hi = mid - 1;
            }
        }
    }
    return -1;
}
```

The check `nums[lo] <= nums[mid]` deserves a second look, because it's the
step interviewers probe. If the left half were rotated, its endpoints would
be out of order and this comparison would be false. So the test is really a
two-question shortcut: "is the left half sorted?" and, if so, "is the target
inside its value range?" Answer both and you always know which half keeps
the answer.

## Complexity

| Approach | Time | Space |
| --- | --- | --- |
| Linear scan | O(n) | O(1) |
| Modified binary search | O(log n) | O(1) |

Note the constraint matters: with duplicates, the comparison
`nums[lo] <= nums[mid]` can be ambiguous when both hold the same value, and
the worst case degrades to O(n). The no-duplicates promise is what keeps
this logarithmic. This is one of the variants collected in
[Binary Search Variants](/dsa/patterns/binary-search-variants).
