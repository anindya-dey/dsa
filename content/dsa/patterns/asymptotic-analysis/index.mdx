When we say an algorithm is O(n log n), we are making a specific and
narrow promise: **as the input grows, the running time grows no faster
than a constant times n log n.** Not "it takes n log n steps", not "it
is fast", just: past some input size, the curve of time-versus-input is
bounded above by c * n log n. That curve language (asymptotic: "near the
limit") is the whole subject, and almost every misuse of Big-O comes from
forgetting which of those three claims was actually made.

The reason the site leads with this pattern is that every other page
prices its algorithms with it. "The brute force is O(n²) and the
two-pointer solution is O(n)" is the shape of every problem page, so
this page defines the notation those sentences use.

## The three notations, and what each promises

Big-O (**upper bound**): f(n) = O(g(n)) means f grows no faster than g.
It is a ceiling: "no worse than". A single loop over n elements is O(n),
but it is *also* O(n²) and O(2^n), both true and both useless, because
Big-O alone never promises tightness.

Big-Ω (**lower bound**): f grows *at least* as fast as g. Ω(n log n)
for comparison sorting is the famous use: no comparison sort can beat it,
a floor, not an algorithm.

Big-Θ (**tight bound**): f = Θ(g) when f = O(g) and f = Ω(g) both hold:
the growth rate *is* g, up to constants. "The algorithm is Θ(n log n)"
is the honest, full promise, and when people say "this is O(n log n)"
they almost always mean Θ(n log n), the useful claim.

The habit worth building: when you state a complexity, ask which claim
you are making. Sorting is Θ(n log n) *by comparisons*, and the Ω
argument (the decision-tree lower bound: n! orderings must be
distinguished, and a binary tree of height h distinguishes 2^h) is the
canonical use of the lower-bound notation.

## The rules of the arithmetic

Complexities compose, and the composition rules are simple enough to
apply mechanically once, then trust forever:

- **Sequential blocks add**: a loop of n, then a loop of m, is O(n + m).
- **Nested loops multiply**: a loop of n containing a loop of n is
  O(n²), *provided* the inner work does not depend on the outer in a
  way that changes its count (see amortized below).
- **Drop constants and lower-order terms**: O(3n² + 100n + 7) is O(n²),
  because past any size you like, the n² term dwarfs the rest. This is
  where the "drop the constant" habit is correct: in the *curve*, the
  coefficient is invisible.
- **Different variables stay different**: a loop over a string of
  length m inside a loop over n words is O(n * m), not O(n²), and
  collapsing distinct variables into one n is a classic mis-analysis.

The last rule has a practical corollary for interviews: state your
variables ("n is the array length, k is the number of queries") before
stating complexity, because most complexity *disagreements* are actually
variable-definition disagreements.

## What Big-O leaves out, on purpose

The notation is about growth, not speed, and three real things sit
outside it:

- **Constants.** An O(n) algorithm doing 100 heavy operations per
  element can lose to an O(n log n) one doing 3. This is why real
  libraries use insertion sort (O(n²)) for tiny arrays, and why
  "asymptotically better but practically slower" is a real category,
  not a mistake.
- **The crossover point.** Curves cross: past some n₀ the better
  asymptotics win, and below it the constants win. For `n <= 20` or so,
  constants usually dominate everything.
- **The memory hierarchy.** The notation counts operations, but the
  machine counts *cache misses*: a linked list and an array can both be
  O(n) to traverse, and the array is many times faster, because
  contiguous memory is prefetched and pointer-chasing is not.

Big-O is a model of cost, chosen because it is simple enough to reason
about, and knowing it is a model (with known blind spots) is what
separates "knows the notation" from "knows the analysis".

## Amortized: paying for the expensive rare case

One more pricing tool that belongs in the basic kit: **amortized
analysis** prices a sequence of operations by averaging the expensive
ones over the cheap ones. The canonical example: appending to a
`std::vector` is O(1) *amortized*, because doubling means n appends
cost O(n) total copying, not O(n) each; and the same argument prices a
[monotonic stack](/dsa/patterns/monotonic-structures) pass ("each
element is pushed once and popped once, so the nested loop is linear
total") and every two-pointer algorithm whose inner loop "runs more than
once" per outer step.

The phrase "each element is pushed at most once and popped at most
once, so the total work is O(n) despite the nested loop" is the standard
amortized argument, and it recurs across this entire site: it is how
[sliding windows](/dsa/patterns/sliding-window/minimum-window-substring),
[monotonic structures](/dsa/patterns/monotonic-structures), and
[quickselect](/dsa/patterns/sorting-and-selection) all justify their
complexities. Amortized cost is a *sequence* guarantee, not a
per-operation one: an individual append can be O(n), and that is fine,
because the promise is about the total.

## Space, and the recursion stack

Complexity applies to memory as well as time, and the one systematic
trap is the call stack: a recursion of depth n uses O(n) space *even
with no arrays allocated*, because each frame lives until it returns.
The [recursion](/dsa/patterns/recursion-and-math) page prices this in
full, but the analysis rule is one sentence: **count the maximum
concurrent state, not the total state ever created.** An algorithm that
allocates and frees O(n) things one at a time is O(1) space; a recursion
holding n frames is O(n).

## The analysis workflow

For any code you are pricing:

1. Name the variables (n, m, k) and what they measure.
2. Count the *iterations*, not the lines: what controls each loop's
   count, and does anything inside change it?
3. Multiply nested, add sequential, drop lower-order terms.
4. Ask "is the inner loop really doing that count every time?" If the
   answer is "less as the algorithm progresses", you may have an
   amortized argument, and the nested-loop multiplication is lying to
   you.
5. State time and space, and mention the recursion stack if any.
