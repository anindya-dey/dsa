title: "Asymptotic Analysis"
summary: "How time and extra memory grow with input size, including Big-O and amortized cost."
---

Reading an array once and comparing every pair of its elements can both
work on a small input. The difference becomes clear when the array grows.
For 100 elements, a full scan visits 100 positions. Comparing every
pair of different positions takes 4,950 comparisons. At 1,000 elements,
those counts become 1,000 and 499,500.

**Asymptotic analysis** describes how an algorithm's work or memory use
grows as its input gets larger. It helps you compare approaches without
depending on one computer's speed. You usually describe that growth with
**Big-O notation**, such as O(n) or O(n²).

## Start by naming the input size

In an array problem, `n` usually means the number of elements. In a graph
problem, you may need two variables: `V` for vertices and `E` for edges.
Say what your variables mean before stating a complexity.

For the array above, a full scan does `n` visits. Comparing every pair of
different positions does `n * (n - 1) / 2` comparisons. The first grows
linearly; the second grows quadratically. Increasing `n` tenfold means ten times as
many scan visits, but roughly a hundred times as many pair comparisons.

We count basic operations, such as comparing two integers, as constant
work. If one operation compares long strings or copies a large object,
include that cost too.

## What O, Ω, and Θ mean

**Big-O is an upper bound on growth.** O(n) means the work is eventually
bounded by a constant times `n`. It does not mean exactly `n` operations
or a particular number of milliseconds.

Suppose a function always performs `2n + 3` basic operations. You describe
it as O(n): the constant multiplier and the extra three operations do not
change its linear growth. O(n²) would also be a valid upper bound, but
O(n) tells you more because it is tighter.

**Big-Ω is a lower bound.** Ω(n) means the work grows at least as fast as
a constant times `n`, once `n` is large enough.

**Big-Θ is a tight bound.** Θ(n) means both the upper and lower bounds are
linear. The `2n + 3` example is Θ(n).

Bounds are not the same as best and worst cases. Searching an unsorted
array may find the value immediately, taking O(1) time in the best case.
If it is absent, you check all `n` elements, taking Θ(n) time in the
worst case. State which case you are describing. An average-case claim
also needs assumptions about which inputs are likely.

## Common growth rates

| Growth | What it looks like |
| --- | --- |
| O(1) | Access one array position |
| O(log n) | Repeatedly halve a search space |
| O(n) | Scan the input once |
| O(n log n) | Efficient comparison sorting, such as merge sort |
| O(n²) | Compare every pair |
| O(2^n) | Visit one bitmask for every subset of n items |

Here, `log n` usually means `log2 n`. Halving 1,024 candidates takes ten
steps, because `2^10 = 1,024`. Changing the logarithm's base changes a
constant factor, not the complexity class.

These are starting points, not speed guarantees. An O(n) algorithm can
be slower than an O(n log n) one on small inputs because its operations
cost more. Memory layout also affects real speed: nearby array elements
often make better use of fast processor memory than scattered linked nodes.
Neither fact changes the growth class. Use the
[cheat sheet](/dsa/cheat-sheet) to estimate a budget from the constraints,
then check time, memory, and total input across test cases.

## Counting loops without guessing

Sequential blocks add their work. A scan of `n` elements followed by a
scan of `m` elements costs O(n + m). If both scans have length `n`, that
is O(2n), which simplifies to O(n).

For nested loops, count how often the inner work actually runs. An inner
loop of `m` steps repeated for each of `n` items costs O(nm). Comparing
each element only with later elements gives
`(n - 1) + (n - 2) + ... + 1`, still Θ(n²). A loop whose counter halves
each time has O(log n) iterations, not O(n).

Do not multiply just because two loops are nested. If an inner pointer
only moves forward and advances at most `n` times across the whole
algorithm, its total work can be O(n). Check that bound rather than
assuming every outer iteration starts a fresh scan.

## Amortized: paying for the expensive rare case

**Amortized analysis** spreads the total cost of a sequence across its
operations. It does not promise that every operation costs the same,
and it does not depend on random inputs.

Consider appending 16 elements to an empty dynamic array. For this
example, let capacities grow as 1, 2, 4, 8, then 16. When the buffer is
full, move the existing elements into a larger one:

```text
Existing elements relocated: 1 + 2 + 4 + 8 = 15
New elements written:                      16
Total element operations:                  31
```

The ninth append moves eight old elements, but all 16 appends together
do only 31 element operations. More generally, this doubling model does
O(n) total work for `n` appends, so each append is **O(1) amortized**.
We assume each element move or write costs O(1).

This explains `std::vector`'s normal append guarantee. C++ does not
require capacity to double. One append can still cost O(n), and forcing
a reallocation before every append defeats the ordinary growth pattern.

The same total-work argument explains a
[monotonic stack](/dsa/patterns/monotonic-structures): each element is
pushed once and popped at most once. Randomized
[quickselect](/dsa/patterns/sorting-and-selection) is different: its O(n)
expected time averages over random pivot choices, while its worst case
is O(n²). Expected and amortized bounds answer different questions.

## Count extra memory too

**Auxiliary space** means working memory beyond the input and required
output. A few counters use O(1) space. A temporary array of `n` integers
uses O(n). Copying an input array counts as extra space, even if the copy
happens when a function is called.

Count the memory held at the same time, not every allocation ever made.
Reusing one temporary integer throughout a scan is O(1) space.
[Recursion](/dsa/patterns/recursion-and-math) also uses memory: depth `d`
with constant-size state per active call needs O(d) stack space. Larger
per-call buffers add to that cost. State explicitly whether your space
bound includes the output.
