## Problem

Given an array `nums` and integer `k`, return an array where element `i`
is the maximum of the window `nums[i..i+k-1]`, for every window of size `k`.

**Constraints**

- `1 <= k <= n <= 10^5`
- `-10^4 <= nums[i] <= 10^4`

**Example**

```text
Input:  nums = [1, 3, -1, -3, 5, 3, 6, 7], k = 3
Output: [3, 3, 5, 5, 6, 7]
```

## Brute force

For each window position, scan the k elements and take the max.

```cpp
std::vector<int> maxSlidingWindowBrute(
        const std::vector<int>& nums, int k) {
    std::vector<int> result;
    for (int i = 0; i + k <= static_cast<int>(nums.size()); ++i) {
        int best = nums[i];
        for (int j = i + 1; j < i + k; ++j) {
            best = std::max(best, nums[j]);
        }
        result.push_back(best);
    }
    return result;
}
```

O(n·k): at the limits, 10^10 comparisons. And again the waste is
structural: consecutive windows share k-1 elements, so each scan rediscovers
a max the previous scan already found.

## Optimal: monotonic deque of candidates

A heap seems natural (it *is* a "max of a set" question), but it fails on
the eviction: elements leave the window by *position*, and a heap can only
remove its top. The fix is to track a **deque of indices**, kept sorted by
their values, where every element that could still be a window maximum
survives and everything dominated is discarded on arrival.

```cpp
std::vector<int> maxSlidingWindow(
        const std::vector<int>& nums, int k) {
    std::vector<int> result;
    std::deque<int> window;                       // indices, values decreasing

    for (int i = 0; i < static_cast<int>(nums.size()); ++i) {
        if (!window.empty() && window.front() <= i - k) {
            window.pop_front();                   // max left the window
        }
        while (!window.empty() && nums[window.back()] <= nums[i]) {
            window.pop_back();                     // dominated forever
        }
        window.push_back(i);

        if (i >= k - 1) {
            result.push_back(nums[window.front()]);
        }
    }
    return result;
}
```

Walk through why the front is always the answer. The deque is decreasing,
so the front holds the largest surviving value, and the front is only ever
removed when its index falls out of the window. Any element popped by the
inner while loop is *both* smaller than the newcomer *and* older, so it can
never again be the maximum of any window both share. It's dead, and
discarding it is safe forever.

Each index enters the deque once and leaves at most once (from one end or
the other), so the whole algorithm is O(n) despite the nested loop, and
each window's answer is read off the front in O(1).

## Complexity

| Approach | Time | Space |
| --- | --- | --- |
| Scan each window | O(n·k) | O(1) |
| Monotonic deque | O(n) | O(k) |

The space bound is O(k), not O(n): the deque can never hold more than the
current window, because anything older has already been popped from the
front. This problem is the standard pairing of
[sliding windows](/dsa/patterns/sliding-window) with
[monotonic structures](/dsa/patterns/monotonic-structures): the window
supplies the eviction rule, and the monotonic structure supplies the
instant max.
