The [latency-vs-throughput](/system-design/fundamentals/latency-vs-throughput)
trade has a *specific, sharp* form in model serving: a **forward
pass is expensive and (for many models) *parallelizable across
requests*** — a batch of 32 requests can be scored in barely more
time than one, because the [GPU](/ai-ml/systems/gpu-accelerator-management)
is built for wide parallel work. So the serving tier's central
optimization is **batching**: collect several requests, run them
through the model together, and split the results back out. The
trade is exact: batching raises throughput (more requests per
expensive pass) and raises each request's latency (it waits for the
batch to fill).

## The batching trade, quantified

The two regimes, and the dial between them:

- **No batching** (batch size 1): the lowest latency (a request
  runs immediately) and the worst throughput (the GPU is mostly
  idle: a forward pass uses a fraction of the parallel units for
  one example).
- **Fixed large batches**: the best throughput (the GPU saturated)
  and the worst latency (every request waits for a full batch).
- **Dynamic batching** (the production answer): the server holds
  requests in a short queue and forms a batch as soon as *either*
  the batch is full *or* a **timeout** (a few milliseconds) fires —
  so a busy server batches naturally (requests arrive fast: the
  batch fills) and a quiet server serves immediately (the timeout
  fires with a small batch). This is the standard mechanism
  (Triton, TorchServe, vLLM all have it), and the two parameters
  (`max batch size`, `max queue delay`) are the tier's
  latency/throughput dial.

```cpp
// The dynamic-batching core: accumulate for up to maxDelay,
// then one forward pass over the whole batch.
struct PendingRequest { Input input; Promise<Output> out; };

void batchLoop() {
    std::vector<PendingRequest> batch;
    auto deadline = now() + maxDelay;
    while (now() < deadline && batch.size() < maxBatch) {
        if (auto req = queue.tryPop(deadline - now())) {
            batch.push_back(*req);
        }
    }
    auto outputs = model.forward(batchInputs(batch));   // ONE pass
    for (size_t i = 0; i < batch.size(); ++i) {
        batch[i].out.resolve(outputs[i]);               // fan back out
    }
}
```

The arithmetic that justifies it: if a forward pass costs `c` (fixed)
plus `k` per example (small), then batch-size-B latency is `c + kB`
and throughput is `B / (c + kB)` — which rises steeply toward
`1/k` as B grows (the fixed cost amortized), so the *throughput*
gain from batching is the amortization of `c`, and the *latency*
cost is the wait for the batch.

## The tail-latency trap

Batching creates a latency hazard that the
[latency page](/system-design/fundamentals/latency-vs-throughput)
warned about, in a sharp form: **the p99 becomes the *queue* wait,
not the model.** A request that arrives just as a batch forms waits
a full batch's processing time *plus* the queue delay; under load,
the queue grows and the tail explodes (the [queueing
theory](/system-design/fundamentals/latency-vs-throughput): at 80%
utilization, the wait is non-linear). The mitigations, and they are
the design's real content:

- **Bound the queue** (a request that cannot be served within the
  latency budget is *shed*, not queued: the
  [backpressure](/system-design/fundamentals/backpressure-and-flow-control)
  discipline, at the serving tier — the honest admission that a
  heavily loaded batching server *must* refuse, or its p99 is
  unbounded).
- **Separate the latency classes** (a real-time request and a
  batch-scoring request should not share a batching queue: the
  [priority queue](/system-design/fundamentals/backpressure-and-flow-control)
  of request classes, so the interactive traffic is not stuck behind
  a bulk job).
- **Measure the queue, not just the model** (the
  [observability](/system-design/fundamentals/observability) signal
  that matters: `model_latency` is stable while `request_latency`
  climbs, and monitoring the former hides the outage — a classic
  serving dashboard bug).

## The LLM case: continuous batching

The autoregressive generation
([streaming](/ai-ml/systems/model-serving-architectures))
changes the batching game, and the technique is worth naming because
it is the modern default: **continuous (iteration-level)
batching**. Because generation is a *loop* (one token per forward
pass, for each request's whole sequence), a naive batch waits for
the *longest* sequence (short requests idle in the batch, wasting
the GPU). Continuous batching re-forms the batch *every iteration*:
a finished request leaves, a new one joins, and the GPU stays
saturated with a *variable* set of sequences — the technique behind
vLLM's throughput, and the reason LLM serving is its own framework
family ([paged attention](https://en.wikipedia.org/wiki/Attention_(machine_learning))
being its memory companion: the [KV cache](/ai-ml/systems/model-serving-architectures)
managed like OS pages, so memory fragmentation does not waste the
GPU).
