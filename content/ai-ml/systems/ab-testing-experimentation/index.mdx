summary: "Randomized experiments for models: assignment, guardrail metrics, and the traps that invalidate results."

An A/B test is the **only** way to answer "is this model change
good for the product?", because every other method (offline
metrics, intuition, dashboards) is a proxy that the
[offline/online gap](/ai-ml/systems/offline-vs-online-evaluation)
exists to distrust. The machinery is a randomized controlled
experiment, and the systems design is the *randomization*, the
*measurement*, and, the part that invalidates most real tests,
the *traps* that break the randomization's assumptions.

## The core: randomize, measure, compare

- **Randomization unit** (who is randomly assigned to control vs.
  treatment): usually the *user* (not the request: the same user
  must see one consistent experience, or the effect is
  diluted/confused), sometimes a device, session, or
  [geo](/system-design/fundamentals/geospatial-indexing) cluster
  (when user-level interference exists: two users in a
  [marketplace](/system-design/hld/ride-sharing-app) affect each
  other, so the unit must be the market: the
  [SUTVA](https://en.wikipedia.org/wiki/Rubin_causal_model)
  assumption, made concrete).
- **Assignment** (a deterministic hash of the unit id into a
  bucket: `hash(user_id) % 100 < 50` → treatment: reproducible,
  consistent across services, and the same user stays in the same
  bucket for the test's duration, the *sticky* assignment that
  makes the experience coherent).
- **Metrics** (the *primary* metric: the one the test is powered
  to move; the *secondary* metrics; and the **guardrail metrics**:
  latency, error rate, safety, revenue, the metrics that must
  *not* regress, and whose violation stops the test regardless of
  the primary: the [SLO](/system-design/fundamentals/reliability-engineering)
  discipline, per experiment).
- **Statistical significance** (the test answers "could this
  difference be chance?": the p-value/holdout framing, and the
  *power* question (did the test run long enough to see a real
  effect?: underpowered tests "find nothing," which is not the same
  as "no effect"), the discipline, not a formality, because
  "we tested it and saw no change" on a 2-day test is the most
  common false conclusion in the field.

## The traps that invalidate results

Each of these has killed real launches, and each is a *systems*
bug, not a statistics one:

- **Sample ratio mismatch (SRM)**: the split *should* be 50/50 but
  the logs show 49/51, which means the assignment or the
  measurement is broken (a filter applied to one arm, a
  [cache](/system-design/fundamentals/caching) serving the wrong
  variant, a bot class hitting one side), and *every* result from
  the test is suspect. The **first** thing to check, always.
- **Novelty and primacy effects**: users react to *change*, not to
  the new model (the first days of a test are a honeymoon or a
  shock), so short tests measure the transition; the fix is longer
  windows and *stable* users (the effect should persist, not
  decay).
- **Carryover and interference**: a user who saw treatment keeps
  behaving differently in the next test (contamination across
  experiments: the fix is washout windows and non-overlapping
  experiments per user), and network effects (the treatment changes
  what the control's users experience: the
  [marketplace](/system-design/hld/ride-sharing-app) example above).
- **Peeking and multiple comparisons** (the p-hacking family: stop
  the test when it looks significant, or test twenty metrics and
  report the one that won: the fix is *pre-registration*, the
  metric and the duration decided *before* the test, and the
  correct multiple-comparison corrections, which are the reason
  serious platforms *forbid* mid-test peeking).
- **The proxy problem, again** (a primary metric that moved but the
  *goal* did not: a click-rate win that lowered long-term
  retention: the [metric-vs-goal](/ai-ml/systems/evaluation-metrics)
  trap, answered by long-horizon metrics (retention, LTV) that run
  *beyond* the test window).

## The platform

The systems that run experiments at scale (the reason "A/B
platform" is an infrastructure team): a **flagging/assignment
service** (deterministic bucketing, config-driven variants, the
sticky assignment, the kill switch, the
[feature-flag](/system-design/fundamentals/reliability-engineering)
machinery), a **metrics pipeline** (the exposure log joined to the
outcome log, the [offline/online](/ai-ml/systems/offline-vs-online-evaluation)
join machinery, the same
[event-sourcing](/system-design/fundamentals/event-sourcing-and-cqrs)
shape), and the **analysis layer** (the significance computation,
the SRM check, the guardrail monitoring). The platform is what
makes experiments *cheap* (a config change and a metric
definition), and cheapness is what makes the org run many, which
is the actual maturity signal, not any single test.

## Where this site already uses it

The [recommendation](/system-design/hld/recommendation-system),
[ad-click](/system-design/hld/ad-click-aggregator), and
[fraud](/system-design/hld/fraud-detection) designs all *depend* on
this platform (their model updates ship through it), and the
[RL/bandit](/ai-ml/systems/supervised-unsupervised-rl)
discussion noted that the same exposure logging is the RL training
data: **the experimentation platform and the learning system are
the same infrastructure**, which is the deep reason every serious
ML org runs one.
