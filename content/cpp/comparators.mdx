Every ordered tool in the standard library can take a comparator: `sort`,
`stable_sort`, `nth_element`, `lower_bound`, `set`, `map`, and
`priority_queue`. They all assume the same contract, called a **strict
weak ordering**. Keep it and they work. Break it and the behavior is
undefined: wrong answers, an endless loop, or a crash on some inputs.

## The contract

A comparator `comp(a, b)` answers one question: must `a` come strictly
before `b`? For the answer to be usable:

- **Nothing comes before itself.** `comp(a, a)` is false.
- **Order carries through.** If `comp(a, b)` and `comp(b, c)`, then
  `comp(a, c)`.
- **Ties are consistent.** If neither `a` nor `b` comes first, they are
  equivalent, and equivalence also carries through.

The everyday violation is `<=` instead of `<`. Then `comp(a, a)` is true,
the first rule fails, and `std::sort` may even read outside the range.
`>` is fine: it is still strict, and it sorts in descending order.

## Common shapes

```cpp
#include <algorithm>
#include <cassert>
#include <set>
#include <string>
#include <tuple>
#include <vector>

struct Person {
    std::string name;
    int age;
};

int main() {
    std::vector<Person> people = {{"cy", 30}, {"al", 25}, {"bo", 30}};

    // Age descending, then name ascending.
    std::sort(people.begin(), people.end(), [](const Person& a, const Person& b) {
        if (a.age != b.age) return a.age > b.age;
        return a.name < b.name;
    });
    assert(people[0].name == "bo" && people[1].name == "cy");

    // The same order with std::tie: swap a and b for the descending field.
    std::sort(people.begin(), people.end(), [](const Person& a, const Person& b) {
        return std::tie(b.age, a.name) < std::tie(a.age, b.name);
    });
    assert(people[0].name == "bo" && people[2].name == "al");
}
```

For several fields, compare the first field and fall through to the next
one only on a tie. `std::tie` builds tuples of references, which compare
field by field, so it does the fall-through for you. Swapping `a` and `b`
for one field, as above, reverses that field's direction.

## Comparators in sets and maps

```cpp
auto byAge = [](const Person& a, const Person& b) { return a.age < b.age; };
std::set<Person, decltype(byAge)> byAgeSet(byAge);
byAgeSet.insert({"al", 25});
byAgeSet.insert({"bo", 25});   // Same age: treated as the same key.
assert(byAgeSet.size() == 1);
```

In a `set` or `map`, two elements are the same key when neither comes
before the other. Ordering people only by age makes two people of the
same age collide, and the second insert is ignored. Add a tie-breaker,
such as the name, when distinct elements can compare equal.

## The heap direction

`std::priority_queue` puts on top the element that would come **last** if
you sorted with its comparator. Sorting with `std::less` puts the largest
last, so it gives a max-heap; `std::greater` gives a min-heap. Read the
comparator as "which element sinks".

## Checking a comparator you invented

When the order is clever, as in
[Largest Number](/dsa/patterns/sorting-and-selection/largest-number)'s
`a + b > b + a`, ask two questions before trusting it. Is it false when
both inputs are equal? Does the order carry through three elements? If you
cannot argue both, the sort may pass your tests and fail on others.
Compiling with `-D_GLIBCXX_DEBUG` on GCC turns many violations into
immediate errors while you test.
