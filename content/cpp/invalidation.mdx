The collected invalidation rules — the one page that every
[container entry](/cpp/vector) points to when it says "and the
invalidation rules that bite everyone once." The subject: **which
operations invalidate which iterators, references, and pointers,
and the idioms that make the common cases safe.**

## The rules, by container

| Container | Insert/erase at end | Insert/erase in middle | Rehash/grow | References stable? |
| --- | --- | --- | --- | --- |
| [vector](/cpp/vector) | erase: ok; **insert: reallocate if grown** | invalidates at+after position | **any growth: ALL invalidated** | NO (growth moves) |
| [string](/cpp/string) | same as vector | same as vector | same as vector | same as vector |
| [deque](/cpp/deque) | iterators invalidated; **references OK** | iterators invalidated; references at ends OK | n/a (block growth) | **YES (elements don't move)** |
| [list](/dsa/patterns/linear-structures) / [map,set](/cpp/map) | **only the erased element** | only the erased element | n/a | **YES** |
| [unordered_*](/cpp/unordered-map) | erase: only that element | erase: only that element | **rehash: ALL iterators** (references OK) | YES (elements don't move) |

The two dimensions that vary: **iterators** (positions: invalidated
liberally) and **references/pointers** (to elements: invalidated
rarely — anything node-based or block-based keeps elements where
they are). The
[vector](/cpp/vector) is the pessimist (growth moves everything);
the [tree containers](/cpp/map) are the optimists (erase touches
one node).

## The erase-while-iterating idiom

The classic bug (erase inside a range-for: the loop's `end`
iterator is invalidated, UB) and the standard fix in every form:

```cpp
// THE BUG (never do this):
for (auto it = v.begin(); it != v.end(); ++it) {
    if (shouldErase(*it)) v.erase(it);      // it is INVALIDATED
}                                          // ++it on a dead iterator: UB

// THE FIX (iterator-returning erase): erase RETURNS the next iterator
for (auto it = v.begin(); it != v.end(); /* no ++ here! */) {
    if (shouldErase(*it)) {
        it = v.erase(it);                   // erase advances FOR you
    } else {
        ++it;
    }
}

// THE ALTERNATIVE (erase-remove): filter with remove_if + erase
v.erase(std::remove_if(v.begin(), v.end(), shouldErase), v.end());
//            ^ shifts kept elements forward ^^^^ truncate the tail
// O(n), no per-erase shift: THE bulk-erase idiom for vectors
```

The [erase-remove](https://en.cppreference.com/w/cpp/algorithm/remove)
idiom's why: `erase` in a loop is O(n) *per erase* (shifting the
tail each time: O(n²) total), while `remove_if` shifts each kept
element once (O(n)) and the final `erase` truncates. For
node-based containers ([map](/cpp/map),
[unordered_map](/cpp/unordered-map)), the iterator-returning
`erase` form is the idiom (no shift, O(1) per erase:
`m.erase(it++)` or `it = m.erase(it)` — the loop form that the
[linked-list](/dsa/patterns/linear-structures) entries write by
hand).

## The other classic traps

- **`reserve`/`push_back` growth inside iteration over the same
  container**: the loop's iterators (captured at loop start) are
  dead after the growth — the [vector entry's](/cpp/vector)
  self-modifying loop. Index-based loops with a re-checked `size()`
  when growing; iterator loops only when not growing.
- **`rehash` (unordered containers) on insert**: *any* insert may
  rehash (size crosses the
  [load factor](/cpp/unordered-map)), invalidating all iterators —
  but *references* stay (the elements did not move), so
  pointer-to-element designs survive where iterator-holding
  designs do not.
- **Dangling by-reference [lambda
  captures](/cpp/function-lambdas)**: not container invalidation,
  the same disease (a pointer into a scope that ended): the
  closure must not outlive what it captured by reference.
- **`c_str()` on a [string](/cpp/string) then modifying the
  string**: the pointer was valid *until the next modification* —
  the [string entry's](/cpp/string) dangling form.

## The rule of thumb

**When you mutate, you do not hold iterators.** Save indices, or
use the mutating-operation's *return value* (erase returns the
next iterator: the idiom), or re-find after mutation — and when
you must hold a stable handle across mutation,
[node-based containers](/cpp/map) hold references where
[vectors](/cpp/vector) cannot.
