`std::vector` is an array that can grow as you add elements, with O(1)
access by index. It is a useful starting choice for an ordinary sequence.

## Contiguous storage and data()

Except for `vector<bool>`, a vector stores its elements in **contiguous
memory**, with each element immediately following the previous one.
Contiguous means adjacent, while continuous usually means uninterrupted.
This guarantee concerns program addresses, not the physical arrangement of RAM.

When the element type `T` is not `bool`, `v.data()` returns a `T*` pointer to the storage, or `const T*`
for a const vector, which prevents changes through the pointer. At a valid
index `i`, `v.data() + i` points to `v[i]`. Adding 1 advances one element,
or `sizeof(T)` bytes, rather than one byte regardless of type.

```cpp
#include <cassert>
#include <vector>

int main() {
    std::vector<int> v = {10, 20, 30};
    int* p = v.data();

    assert(p == &v[0]);
    assert(p + 2 == &v[2]);
    assert(*(p + 2) == 30);
}
```

The assertions check the pointer arithmetic. An empty vector has no element
to dereference, even if `data()` is non-null. Saved element pointers become
invalid after reallocation or destruction.

## Size, capacity, and growth

`size()` counts existing elements. `capacity()` counts how many fit in the
current allocation. Exceeding capacity requires **reallocation**: obtaining
a larger buffer and moving or copying the existing elements into it.

```cpp
std::vector<int> scores = {10, 20, 30};
scores.reserve(5);  // Size is still 3; capacity is at least 5.
assert(scores.size() == 3 && scores.capacity() >= 5);
scores.push_back(40);
scores.resize(5);   // Adds one int initialized to 0.
assert((scores == std::vector<int>{10, 20, 30, 40, 0}));
```

`reserve` prepares storage without changing size; `resize` changes the
number of elements. Reserve once when you know the expected final size.
That call may reallocate, but subsequent appends do not while size remains
within capacity. `clear()` removes all elements but keeps capacity;
`shrink_to_fit()` requests less storage, but the library may ignore the request.

Appending with `push_back` is
[amortized O(1)](/dsa/patterns/asymptotic-analysis#amortized-paying-for-the-expensive-rare-case).
One append may relocate every existing element, but n ordinary appends
from empty take O(n) total element moves or copies. Typical libraries grow
capacity geometrically, although the exact growth factor is not specified.

## Accessing and removing elements safely

Both `v[i]` and `v.at(i)` provide O(1) access. The difference is checking:
`at` throws `std::out_of_range` for an invalid index, while an out-of-range
`[]` access is undefined behavior in C++20. The language does not define
the outcome: it may crash or appear to work. `front()`, `back()`, and
`pop_back()` require a nonempty vector.

An **iterator** represents a position used to traverse a container;
`end()` represents the position just past its last element. A pointer or
reference can also identify an element, but these saved handles do not
survive every modification:

- Reallocation invalidates all element pointers, references, and iterators.
- Without reallocation, insertion or erasure invalidates handles at or
  after the changed position. Earlier elements remain valid.
- Every `push_back` invalidates the old `end()`, even without reallocation.

Do not append inside a range-based loop over the same vector: the loop
holds iterators that appending invalidates. To process only the original
elements, save their count and use indices, copying each value before an
append that might reallocate.

Middle insertion and erasure take O(n), where n is the number of elements,
because existing values may need to shift.
For bulk filtering, C++20's `std::erase_if` removes elements satisfying a
condition in one linear pass, rather than repeatedly shifting the remaining
elements after individual erasures.

## Why `vector<bool>` is different

`std::vector<bool>` commonly packs values into individual bits. It does not
guarantee an array of addressable `bool` objects, so there is no portable
`bool*` interface through `data()`, and the ordinary pointer-arithmetic
rule does not apply.

Mutable `bits[i]` returns a **proxy**, a small handle that reads or writes
a bit, not a `bool&`. `auto` preserves that proxy; `bool` copies its value:

```cpp
std::vector<bool> bits = {true, false};
auto bit = bits[0];  // Proxy referring to the first bit.
bit = false;        // Changes bits[0].
bool value = bits[0];
bits[0] = true;     // value remains false: it is an independent copy.
assert(bits[0] && !value);
```

Use `std::vector<char>` for contiguous byte-sized flags. `std::deque<bool>`
gives real bool references but is not contiguous.
[`std::bitset`](/dsa/patterns/bit-manipulation) offers fixed-size bits;
`vector<bool>` remains an option for a dynamic size.

## Choosing vector in practice

Sequential reads can reuse nearby elements fetched together in a **cache
line**, a block of memory held in the CPU cache. Hardware prefetching may
also fetch upcoming data early. It is commonly enabled on modern CPUs,
not a vector setting or a C++ guarantee. Random access can lose this benefit.

Contiguous storage does not guarantee maximum **memory bandwidth**, the
amount transferred per second; calculations may limit your loop instead.
Linked-list nodes may already be cached, so each step need not cause a
**cache miss**, where needed data is absent. Actual speed depends on the
workload, not just the container's layout.

Choose by required operations first: a deque supports efficient front
insertion, while a hash table supports key-based lookup. If several choices
fit, benchmark realistic sizes, element types, and access patterns. Compare time, memory
use, and latency spikes in optimized builds, keeping results observable
so the compiler cannot eliminate the work.
