The "small aggregates": `std::pair` (two heterogeneous values),
`std::tuple` (N heterogeneous values), and `std::array` (N
same-typed values, on the stack). Their shared superpower is quiet
and load-bearing across this entire site: **lexicographic
comparison**, which is why pairs of `(key, value)` sort the way
you want and why tuples of `(distance, node)` pop from a
[priority queue](/cpp/priority-queue) in the right order.

## pair: the two-field workhorse

```cpp
std::pair<int, std::string> p = {3, "abc"};
auto [num, str] = p;                  // structured bindings (C++17)
p.first; p.second;
std::make_pair(3, "abc");              // deduce types
p < q;                                // LEXICOGRAPHIC: first, then second
```

The comparison rule, stated once because it powers half the
algorithms on this site: **`a < b` compares `a.first < b.first`,
ties broken by `a.second < b.second`** — pairs sort the way a
[dictionary sorts two-word phrases](/cpp/string), and the
consequences:

- A [vector of pairs](/cpp/vector) + `std::sort` is a "sort by X,
  then Y" for free (the compound-comparator idiom).
- A `priority_queue<pair<int,int>>` is a max-heap by first, ties
  by second — and `pair<int, pair<int,int>>` extends it (the
  [Dijkstra](/dsa/patterns/graph-specializations/problems/network-delay-time)
  idiom: `(distance, node)` pops nearest-first with a *min-heap
  comparator*, ties broken by node id, all from one type's
  comparison).
- `std::map` with a pair key is "a two-dimensional sparse index"
  (the lexicographic order does the row-major layout).

## tuple: the N-field generalization

```cpp
std::tuple<int, std::string, double> t = {1, "x", 2.5};
auto [i, s, d] = t;                   // structured bindings
std::get<0>(t);                       // by index (types may repeat)
std::get<std::string>(t);             // by type IF unique
std::make_tuple(...);
t < u;                                // lexicographic, all fields in order
std::tie(a, b) = somePair();          // unpack into EXISTING variables
```

`std::tie` is the idiom worth knowing (unpacking into existing
variables rather than declaring new ones), and
[structured bindings](https://en.cppreference.com/w/cpp/language/structured_binding)
are the modern form that replaced it for most cases. The
[map iteration](/cpp/unordered-map) idiom
(`for (auto& [key, value] : m)`) is the same mechanism binding the
map's pair-typed elements.

## array: the fixed-size, stack-allocated array

```cpp
std::array<int, 26> counts{};         // {} zero-initializes: the idiom
counts.size();                        // constexpr: known at compile time
counts[0];
counts.fill(x);
std::sort(counts.begin(), counts.end());  // full container interface
// Unlike C arrays: it COPIES (assignable, passable by value),
// knows its size, and works with the algorithms.
// Unlike vector: no resize, no heap: stack storage, fixed N.
```

`std::array` is the answer where this site's code writes
`std::array<int, 26>` for letter counts and `std::array<TrieNode*, 26>`
for [trie children](/dsa/patterns/trie-prefix-tree): a
compile-time-sized, contiguous, zero-initializable aggregate — the
C array's semantics with a real type's interface. The
`{}`-initializer ("all zeros") is the idiom that C arrays lacked.

## The collective lesson

All three are **aggregate types with derived comparison**: they
carry their values and *define* their order, which is the
difference between a container's elements and a bag of fields.
When a solution on this site sorts `pair`s, pops `pair`s, or maps
`touple`s, the type's lexicographic comparison is doing quiet
algorithmic work — the same work a hand-written comparator does
when the natural order is not enough, which is when
[the lambda entry](/cpp/function-lambdas) takes over.
